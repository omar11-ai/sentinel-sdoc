The problem

One shipped bill of lading, checked by hand, against an instruction that reads almost the same

Averis' documentation team does this all day. The differences that matter are small, and the differences that don't are frequent.

From this dataset — email_013, port of discharge:
SI: MOMBASA, KENYA (KEMBA)  ·  BL: TUTICORIN, INDIA (KEMBA)
The UN/LOCODE is identical. The port is not. The "clever" approach — normalise ports to their code — silently passes this defect.

What we built

A working verification desk, deployed — not a demo on three emails

Every number on this slide is measured on the full 520-email dataset through the organizers' official scorer.

  • Classification — 520/520 into the five categories; keyword cues fast-path the clear cases, the LLM takes genuinely ambiguous subjects
  • Extraction — typed readers for txt / pdf / xlsx / docx; every value keeps its source line as evidence
  • Comparison — seven fields, rule-named verdicts; ports compared by name with the code as evidence only
  • Escalation — four canonical review reasons, ordered, each one reachable and each one audited
  • Reviewer round trip — confirm / correct / accept-variation / unresolvable; corrections recompute the verdict through the pipeline, they never overwrite it
  • Full audit chain — append-only reviews + audit events; the submission is rebuilt from current state so report and data can never disagree
  • Live AI — any email can be re-decided end-to-end on demand; a Generalize Lab processes novel-format documents live
  • Self-check — the deployment scores its own submission through the official scorer and publishes the result

Implementation details

The details that make it verifiable

Evidence, not just verdicts

Every extracted value keeps its source line; every mismatch shows the literal SI and BL lines side by side in monospace — alignment is how the eye finds a difference.

Corrections recompute

A reviewer correction re-enters normalization, the comparison re-runs, and the verdict is recomputed — with an optimistic-concurrency version check and the full before → after in the audit log. Original extractions are never mutated.

Contract-first submission

validate_submission.py gates the exact sample_submission shape: id set, enums, cross-field consistency, strict JSON — checked before anything is uploaded.

Deterministic core, AI at the boundary

The comparison core gives one answer per input. The LLM handles what has no lexical route: ambiguous subjects, novel field labels, and on-demand live re-decision — through a content-hash cache with retries.

Bilingual labels handled

The corpus carries English/Chinese labels (毛重, 发货人, 箱数…). CJK ranges are stripped before matching — a naive parser silently drops about a third of pairs.

Injection-resistant

Six prompt-injection patterns detected in document text; matched content is treated as data and reported — never obeyed.

Challenges faced — reading the corpus

Three traps that defeat the obvious approach

Each of these was found by profiling the actual attachments, not by assuming.

1 · The LOCODE trap

Up to 26 pairs change the port name while keeping the same UN/LOCODE. Normalising to the code — the sophisticated move — manufactures false negatives. Rule shipped: compare names; the code is corroborating evidence only.

2 · The address-carryover trap

Consignee changed but its address block copied across. Comparing whole blocks merges distinct entities. Rule shipped: entities compared on the name sub-field.

3 · The substring trap

Group-entity names where one is a prefix of the other score near-100 on partial similarity. Rule shipped: thresholds tuned by experiment against the scorer, not intuition.

…and the quiet ones

Bilingual EN/中文 labels on ~a third of pairs · an unfilled template placeholder (Gross Wt: ____MT) that must be missing_value, not a number · 2 truncated PDFs that are unreadable rather than wrong-type, so readability is checked before document type is asserted · edge-case emails 496–520 spanning all four escalation reasons.

Challenges faced — engineering

The build fought back too

The minifier that silently dropped the design

The CSS pipeline rewrote backdrop-filter: url(#filter) to a -webkit-only form that Chrome ignores — the liquid-glass design shipped invisible. Caught by computed-style assertions in the browser, fixed by switching the CSS minifier. Lesson: verify what the browser computed, not what the source said.

Overlay, never overwrite

Letting a reviewer edit stored verdicts directly would let the report and the underlying data disagree — the exact bug class this product exists to catch. The reviewer overlay recomputes instead, which cost more design and bought the audit story.

Free-quota discipline

Batch LLM usage is env-gated, content-hash cached and retried on 429/5xx; the deterministic core carries the batch so a quota wall degrades capability, not correctness.

Truth as a pipeline

The deployment scores itself through the official scorer on every run, so the published scoreboard can never drift from the code — the same scorer the organizers will run.

Future roadmap

From verified prototype to production desk

Reliability first

Managed Postgres behind the existing store interface · queue + worker for batch runs with inline fallback · per-review-reason escalation thresholds · dead-letter replay and chaos tests.

Reviewer operations

Authentication with reviewer roles and assignment · approval chains · keyboard-first review · in-document highlighting of the exact mismatched spans.

Generalisation

OCR lane behind the existing reader interface for image-only paperwork · carrier-specific alias packs learned continuously from reviewer corrections · the comparison rule explorer surfaced to supervisors.

Interoperability

DCSA eBL 3.0-flavoured export as a serializer · webhook events for downstream systems · the seven-field contract generalised to additional document types.

The AI boundary does not move: deterministic where one input must have one answer; AI where language is genuinely ambiguous.
